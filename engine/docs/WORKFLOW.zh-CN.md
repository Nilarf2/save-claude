# 从设计到发布的中文制作流程

本仓库提供确定性运行时、数据校验和通用审核工具；游戏负责故事、美术、舞台宿主、服务配置与发行。任何自动检查都不能替代发布前的人工剧情、美术、隐私和授权审阅。

## 源文件与产物的权威

| 内容 | 权威来源 | 派生产物/职责 |
| --- | --- | --- |
| 世界观、人物、路线约束 | 游戏的设计文档与批准记录 | 编写和审核的约束，不直接驱动运行时 |
| 完整剧本与显式舞台 | 游戏指定的一份可编辑源（Markdown/JSON 任选一种） | 游戏编译器生成运行 JSON 与源映射；禁止双向手改 |
| 最小示例 | `examples/minimal/story.json` | 示例没有另一个 Markdown 源；JSON 本身就是权威 |
| 引擎实现 | `packages/*/src` 与提交版本 | `dist/`、`packages/*/dist/`、游戏 vendor/runtime 都是构建产物 |
| 正式角色身份与服饰 | 游戏批准的原作/授权参考及基准图 | 表情/动作是同一基准的变体；临时试稿没有替换权 |
| 正式资源选择 | 游戏中的资源/立绘清单 | 审核页只展示清单引用的图片，不自动挑“最新”文件 |
| 审核页、截图和路线证据 | 当前源编译出的运行数据 | 只读快照，源改变后重建，不从审核页回写剧情 |

一项修改只能有一个正式入口。若游戏已有 Markdown → JSON 编译器，应先改 Markdown、再编译并更新源映射。引擎不规定游戏源文件名，也不包含游戏专属编译器、角色提示词、对白或参考图。

## 1. 设计与约定

先明确题材、成年角色身份、玩家目标、失败条件、结局范围、篇幅和各端输入方式。列出每条主线/侧线入口、关键选择、条件、即时反馈、延迟回收与合流位置。变量说明类型、初值、上下界和读写位置；标签说明何时建立与消费。采用稳定的场景、节点、选项、资源、角色和表情 ID，删除/重命名前考虑旧存档迁移。

制作资源清单：每个地点需要的背景状态，每个角色实际用到的表情、姿势与道具，音乐/环境音/音效及授权来源。先完成短而完整的纵向样片：开场 → 选择 → 状态变化 → 合流/结局 → 保存/恢复，不先堆大量未接线正文。

## 2. 编写正文与分支反馈

使用 `templates/剧情填写模板.md` 与 `templates/prompts/story-review.md` 的约定。正文不写“此处待补”；每个选项应有可见反馈，且后续角色反应与状态一致。核对相同分支重复游玩、先做侧线再回主线、条件隐藏/禁用时的提示。没有可选项的 `choice` 要写 `fallback`；否则运行时会抛错并回滚，防止静默卡住。

把主题与人物语言审阅交给人工，数据校验只能检查形式和引用，无法证明角色塑造或叙事质量。

## 3. 接线与内容验证

将完整源经游戏编译器转换为 `Story`；输出带章节标题/源行号的独立源映射，供审核页显示。编译器处理选择、条件、反馈节点、状态变化、舞台和资源引用，不能通过事后手改产物修补接线。运行：

```sh
npm ci --ignore-scripts
npm run typecheck
npm run build
npm run story -- validate examples/minimal/story.json
```

`validateStory` 检查基本类型、重复节点/选项、目标节点、变量/visited 引用、音频参数及模块校验，并报告静态不可达节点。JSON Schema 是编辑器辅助，实际编译使用 `validateStory`。带扩展字段的游戏还必须使用自己的模块注册表/验证器；纯 CLI 默认没有游戏模块。静态可达只说明有边，不能证明真实条件能够通过。

引擎命令同步且有事务边界；动作、PRNG、事件、效果和视图构造全部成功才提交。模块直接做的外部副作用无法回滚，网络、音频和存储工作必须留在宿主。条件和视图检查应纯净，不能把读取选项当作执行动作。

## 4. 显式舞台与恢复

引擎内置 `scene` 管背景/场景和持久音乐/环境音；**角色群像舞台不是内置字段**。游戏应通过模块（例如 `stage:set` 动作）记录在场角色、左右/中间站位、表情、姿势、道具与层级，保存在模块状态；宿主按返回效果渲染。自定义数据需要对应的模块验证器，不要只把额外字段塞进 JSON 然后假定核心会执行。

每次建立新场景显式清空/重建舞台，必要时在每段镜头或台词前更新。旁白时仍保留应在场的角色；没有台词的角色也可以留在舞台。不要通过“谁在发言”推断唯一在场角色，不因旁白而清空立绘，也不要从图片文件名猜姿势。

存档恢复不重跑 `onEnter`；宿主需从 `StepResult.state`/快照模块状态重建舞台，包括清除恢复前但新档里没有的背景/角色。持久音轨通过恢复效果或 `WebAudioAdapter.reconcile()` 对齐，SFX 不补播。模块请求按当前 requestId 恢复，不能把旧请求结果送给新会话。检查对话中途、选择前、模块等待和结局的保存/恢复。

## 5. 美术一致性与完整构图

先整理原作/授权参考，批准单一角色基准，再做表情和动作。提示词明确脸、眼、发型、发饰、头纱、衣服结构与配色，不把“改表情”变成重设计服饰。参考图与游戏提示词留在游戏私有美术目录，不复制进引擎。

从 `templates/prompts/portrait.md` 与 `background.md` 开始填写；实际调用服务和费用由项目配置。公共生图工具默认预览，只有显式 `--execute` 才发一次请求。保留原始输出和处理记录，不把透明棋盘格画进图里。

要求头顶、完整头发/头纱外轮廓、手/手指和全部道具收入构图，上方及左右留出安全距离；半身只在明确的下沿有意截断。生产尺寸应按宽和高同时 contain 等比缩放，不能只按高放大再切掉左右。背景 cover 与角色 contain 是不同的布局策略。

离线工具 `prepare-sprite.py` 先检查输入主体贴边，再裁透明空白/加边。上/左/右贴边意味着需检查原图；加透明画布不能补回已切掉的发丝、头纱、手和道具。出现缺失就重新生成或局部补绘，然后重审。抠图后核对细发丝、衣物同色区、透明道具、色溢和半透明边；边缘算法只是辅助。

## 6. 可视化审阅

```sh
node tools/authoring/build-story-map.mjs --story examples/minimal/story.json --out build/story-map --revision working-copy
python3 tools/authoring/build-portrait-review.py --manifest game/portraits.json --asset-root game/web --out build/portrait-review
```

剧情页按章浏览节点和边，点击每条选择看条件、禁用提示与数值/标签变化，查侧线返回、合流与结局，回到源映射修正文。地图是编译快照，不是证明条件能通的游戏模拟器。自定义模块动态跳转若没有静态目标，需游戏 adapter 提供可审阅元数据。 地图同时给出静态未可达、非结局死路和无已知结局路径提示；条件只按可能边处理，遇到动态目标/宿主依赖会标明无法判断，不把这些提示当作已执行路线结论。

立绘页只显示正式清单里的资源，左右对照暗底/亮底并可切棋盘格；检查同一角色不同表情/动作的脸、服饰与道具一致。随后在实际游戏中看站位、缩放、对话框遮挡和上下边界。不能只看缩略图或用未经登记的试稿替代正式资源。

## 7. 真实路线验收

每条计划发布的主线/结局至少保留一条从正常起点推进的玩家路线。使用真实选择顺序、固定种子和预期节点，核对结局 ID、关键变量/标签。禁止通过强改变量、改存档或直接跳结局冒充通关证据。侧线和条件边界补少量针对性路线，避免重复跑大量同类路径。

```sh
npm run check:flow
npm test
npm run check:example
node tools/authoring/check-route.mjs --story game/story.json --route game/routes/ending-a.json --modules game/modules.mjs --out build/routes/ending-a.json
```

路线证据可在地图页面用文件选择器导入，或构建地图时增加 `--trace build/routes/ending-a.json`。导入校验故事 ID、内容版本、结局快照和停顿结构；按正数 visits 高亮实际记录的节点，按 trace 浏览玩家停顿。现有证据没有逐步输入命令或完整自动边顺序，页面会明确说明，不猜边、不执行游戏。结构校验不是重新通关或文件真实性证明，更新源后须重新生成证据。

路线工具的模块文件默认导出数组。游戏若有宿主异步机制，需要由游戏自己的无外部副作用测试 adapter 模拟，并另做实机检查。实际加载、音频解锁、触摸、舞台、媒体和浏览器存储不由命令行路线证明。没有执行的路线明确写“未验证”。

## 8. 多端与打包

先构建最小示例确认引擎和部署路径：

```sh
npm run example:build
python3 -m http.server 8000 --bind 127.0.0.1 --directory build/minimal
```

在浏览器打开 `http://127.0.0.1:8000/`。示例不含游戏内容与外部图片，支持两条选择、结束、保存、读取和重开。浏览器 ES module 使用 importmap，核心通过 `@text-adventure/save` 校验快照，因此 vendor 必须同时提供五个运行包。

游戏构建只复制正式运行目录到全新的发行目录，使用明确的文件清单。至少人工检查桌面键鼠、手机触摸与竖屏、平板布局，字体/文本溢出、按键焦点、滚动、立绘上下边界、背景裁切、音量/静音/手势解锁、重载和存档。若声明离线可玩，断网检查全部所需资源；使用子路径托管时检查资源相对路径。浏览器 `file://` 不等价于 HTTP 部署；最小示例需本地 HTTP 服务。

桌面/移动打包器、服务 worker、平台商店描述和签名由游戏负责，本引擎不内置。不要在同一个变更里引入无验证的新打包链。CI 仅执行一组小型 Node/Python 回归和示例路线，不声称覆盖真实多端设备。

## 9. 隐私、来源与发布前人工审阅

凭据只使用宿主进程环境或项目批准的密钥管理，绝不写入源代码、提示词、资源清单、日志、截图和发行包。公共仓库/包中移除 `.env`、令牌、用户目录和机器绝对路径、聊天原文、内部交接记录、私有参考图、源图元数据与临时草稿。扫描结果只报告文件和敏感项类别，不显示值。

工作树清理不等于 Git 历史清理；发布前独立检查历史、提交作者隐私与旧远程引用。曾进入历史的密钥须先撤销/轮换，再按项目流程处理历史。仓库可见性、历史重写、推送和发布由有权限的人明确批准，不能把“本地检查通过”当作公开授权。引擎工具不自动执行这些动作。

逐项人工审阅：剧情完整与路线证据、角色美术与完整轮廓、正式资源清单、音乐/字体/原作/模型产出的使用权、第三方许可与署名、隐私清理、多端检查和已知限制。引擎许可与游戏/美术/音乐许可分别确认，不能因引擎开源而推定全部游戏资产也可公开。

最后生成一个可复现发行目录与简明验证记录。人工批准后才执行推送/发布。可视化审核页面和完整路线快照默认留作私有制作产物；需要公开时再单独审阅其中的剧情与资源。

## 10. 固定版本集成到游戏

游戏记录引擎仓库地址及精确提交 ID。只从该版本构建并复制 `packages/{module-api,content,save,core,web-adapter}/dist/index.js`（另选 `.d.ts` 供开发），在游戏中以只读 vendor/runtime 保存；importmap/构建别名保持 `@text-adventure/*` 映射。源与产物必须来自同一版本，不维护另一份可随手改的引擎源码。

需要制作工具时另外保存同版本的 `tools/authoring/`（包含完整 `story-map/`，尤其共用校验脚本 `review-data.js`）与 `tools/image/`、`templates/prompts/`、本中文流程。CLI/路线工具依赖 workspace 包路径，应在引擎 checkout 中运行，或由游戏自己的 adapter 调用 vendor 后保持参数接口。纯静态地图生成、立绘审核和 Python 美术工具可以直接使用工具快照。

游戏专属的 Markdown 编译器、舞台模块、资源清单、路线数据、提示词、参考图、API 提供方配置和发行器继续由游戏维护。升级引擎时更新版本记录、重新构建 vendor、重跑本次影响的真实路线与存档回归，再重建审核页。不要同时存在两份声称为权威的引擎实现。

本轮真实使用的上游设计参考与许可摘要见 [REFERENCES.zh-CN.md](REFERENCES.zh-CN.md)。没有复制上游实现或加入其运行时依赖。
